### Зачем нужен третий параметр

Одна почта заводится в нескольких организациях Pyrus — для инженера внедрения это обычное дело. Без уточнения сервис не понимает, кому именно выдавать токен. В API Pyrus параметр называется `person_id` и означает **сотрудника**, а не организацию; в SDK `pyrus-api` он объявлен в `AuthRequest` с той же оговоркой.

Проверено на живом API: без этого параметра `/auth` отвечает `500 server_error`, с ним — осмысленным кодом. То есть отсутствие `person_id` выглядит как поломка сервиса, хотя дело в неоднозначности организации.

## Состояние доступа на 10.08.2026

**Авторизация не проходит.** `/auth` отвечает `401 invalid_credentials — Invalid login/secret_key` при любом варианте: с `person_id` строкой, числом и без него.

Что проверено, чтобы исключить наши ошибки:

| Проверка | Результат |
| --- | --- |
| Имя параметра организации | `person_id` — верное. С ним ответ 401, без него 500, то есть параметр принимается |
| `organizationId` из devtools | **Не подходит.** `/auth` не знает такого параметра ни как `organizationId`, ни как `organization_id`, ни как `orgId` — во всех случаях ответ 500, тот же, что и без параметра. Идентификатор организации и `person_id` — разные вещи |
| Значение `167110` строкой и числом | Одинаково, 401 |
| Наш собственный ключ | Работает, формы выгружаются — значит, дело не в сети и не в коде |

Вывод: отклоняется именно пара логин + ключ. Вероятные причины — ключ выпущен для другого логина (у ботов Pyrus логин вида `bot@<guid>`), ключ отозван или перевыпущен, либо `167110` не соответствует этому логину.

### Что нужно, чтобы закрыть вопрос

Три значения из аккаунта клиента, взятые вместе, одной парой:

1. **Логин интеграции** — тот, для которого выпущен ключ.
2. **Ключ интеграции** — действующий, не отозванный.
3. **`person_id`** — идентификатор **сотрудника** в организации клиента, а не организации. Значение `167110` взято из `organizationId` в devtools и в этой роли не работает: Pyrus принимает параметр, но не находит по нему сотрудника и отвечает `invalid_credentials`.

   Где искать: в ответах API Pyrus поле называется `person_id` (в веб-интерфейсе в devtools — `personId`). Его же возвращает `/auth`, когда почта заведена ровно в одной организации.

Как только доступ заработает, состав форм `2441923`, `1101763` и `2441100` выгружается командой ниже, и спецификация полей перестаёт быть неполной:

```bash
npm run pyrus:dump -- --client=02 --forms
npm run pyrus:dump -- --client=02 --form=2441923
```
