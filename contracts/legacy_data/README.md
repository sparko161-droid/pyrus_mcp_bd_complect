# Два инструмента для проекта по бизнес-процессам в Pyrus

Здесь лежит то, что вы просили: **сборщик**, который вытаскивает точное описание
чужого MCP-сервера, и **банк решений** — свой MCP-сервер с версионным
хранилищем на Postgres + pgvector.

```
project/
├── collector/          сборщик-интроспектор чужого MCP
│   ├── mcp_introspect.py     выгрузить всё, что сервер СООБЩАЕТ о себе
│   ├── make_report.py        превратить выгрузку в TOOLS.md и COVERAGE.md
│   ├── apiscope.py           логирующий прокси: что сервер ДЕЛАЕТ на самом деле
│   ├── probe_tools.py        прогнать инструменты через прокси → карта эндпоинтов
│   ├── mock_mcp_server.py    заглушка MCP для проверки без боевого сервера
│   └── fake_pyrus.py         заглушка Pyrus API для проверки связки
├── lab/                лаборатория по самому Pyrus API
│   ├── pyruslab.py           измерить окна, границы, флаги, лимиты на ваших данных
│   └── fake_pyrus_rich.py    заглушка с 3046 задачами для проверки лаборатории
└── bank/               банк решений
    ├── schema.sql            схема Postgres + pgvector
    ├── server.py             MCP-сервер, 14 инструментов
    ├── smoke_test.py         сквозной тест: запись → промоушен → поиск
    ├── _test_shim.py         тестовая прослойка (в прод не идёт)
    ├── requirements.txt
    └── docker-compose.yml
```

## Три инструмента — три разных вопроса

Их легко перепутать, а отвечают они на разное:

| Вопрос | Чем |
|---|---|
| Что чужой сервер **сообщает** о себе? | `mcp_introspect` → имена, схемы, аннотации |
| Что он **делает** на самом деле? | `apiscope` + `probe_tools` → реальные вызовы к Pyrus |
| Как ведёт себя **сам Pyrus**? | `pyruslab` → напрямую, без посредника |

Третий вопрос — про периоды, фильтры и лимиты — решается **без** чужого сервера.
Прокси там лишнее звено: меньше контроля, нужен туннель, и вы зависите от чужой
доброй воли.

## Порядок действий

**Сначала сборщик — до всякого кодирования.** Пока вы не знаете точный список
инструментов railway-сервера и их схемы, любая доработка gdigora — это работа
вслепую. Сборщик даёт спецификацию за пять минут.

Дальше сборщик и банк независимы, делайте параллельно.

# 1. Сборщик

## Зачем

Документация railway-сервера говорит «57 инструментов» в одном месте и «58» в
другом. `get_bots`, `create_list`, `delete_list` не соответствуют ни одному
методу в публичном API Pyrus. Что там на самом деле — можно только спросить у
самого сервера. Сборщик спрашивает и раскладывает ответ по полочкам.

Заодно это ваша страховка в переговорах: если автор не отдаёт исходники, но даёт
доступ, полная схема каждого инструмента — почти то же самое для целей
собственной реализации.

## Запуск

```bash
pip install httpx

export MCP_URL=https://pyrus-mcp-production.up.railway.app/mcp
export MCP_BEARER=<токен от автора>
export PYRUS_LOGIN=you@example.com
export PYRUS_SECURITY_KEY=<ваш ключ Pyrus>

python3 collector/mcp_introspect.py --out inventory.json
python3 collector/make_report.py inventory.json
```

Получаете три файла:

| Файл | Что внутри |
|---|---|
| `inventory.json` | машиночитаемо: имя, описание, полная JSON Schema, аннотации по каждому инструменту |
| `TOOLS.md` | каталог для чтения людьми: сгруппирован, с параметрами, пометками «пишет» / «необратимо» |
| `COVERAGE.md` | сверка с 58 методами Pyrus API + **список инструментов, не соответствующих ни одному методу** |

Последняя таблица в `COVERAGE.md` — самая ценная. Каждая строка там означает
одно из трёх: составная операция поверх нескольких вызовов API,
недокументированный эндпоинт Pyrus, или собственная логика сервера. Все три
случая вам интересны.

## Что уже проверено

Сборщик прогнан на заглушке, которая нарочно вредничает:

- обычный JSON и поток SSE в ответ на POST — разбираются оба;
- постраничная выдача `tools/list` через `nextCursor` — 7 инструментов за 3 запроса;
- обязательный `Mcp-Session-Id` после `initialize` — подхватывается и подставляется;
- `prompts/list` отвечает ошибкой — не роняет выгрузку, просто отмечается;
- нет токена — внятное сообщение и код возврата 2, а не трассировка.

Проверить у себя, ничего не подключая:

```bash
python3 collector/mock_mcp_server.py --port 8765 --sse --paginate 3 --session &
python3 collector/mcp_introspect.py --url http://127.0.0.1:8765/mcp --bearer test
```

## Что `tools/list` отдаст, а что нет

Это важно понимать до запуска, чтобы не ждать лишнего.

**Отдаст:**

- точные имена всех инструментов — конец разночтениям «57 или 58»;
- описание каждого своими словами автора. Именно сюда обычно и утекает
  эмпирика: их руководство прямо содержит вещи вроде «`root_id` — это id
  первой версии, и он не меняется» и «`guid` одноразовый»;
- **полную JSON Schema параметров**: типы, обязательность, значения по
  умолчанию, перечисления. Вот перечисления особенно ценны. Список
  `channel.type` — `telegram`, `whats_app`, `max_messenger`, `viber`, `vk`,
  `avito_messenger`, `avito_job` — в публичной документации Pyrus вы не
  найдёте, а из схемы он придёт дословно;
- аннотации: пишет инструмент или только читает, необратим ли он;
- `outputSchema`, если автор его объявил, — это форма ответа.

**Не отдаст:** какой HTTP-метод и путь Pyrus за инструментом стоит, сколько
запросов он делает, в каком порядке, с каким телом. Сопоставление
«инструмент → эндпоинт» в `COVERAGE.md` — это **моя догадка по имени**, а не
факт от сервера. Ровно поэтому там есть колонка «не ложится на
документированный метод»: она честно говорит «не знаю».

Именно недостающую половину достаёт следующий шаг.

# 1б. apiscope: увидеть, что сервер делает на самом деле

## Идея

Railway-сервер принимает параметр `api_url` в **каждом** инструменте — это его
штатная возможность для работы с контурами клиентов. Наведите `api_url` на свой
прокси, и сервер по вашей же команде пойдёт через него. Прокси запишет каждый
исходящий запрос и передаст дальше в настоящий Pyrus.

Чёрный ящик становится стеклянным, причём законно: это ваш трафик, ваши
реквизиты Pyrus, штатный параметр. Ничего чужого не вскрывается — исходники
сервера так и остаются закрытыми, вы просто смотрите на его поведение снаружи.

## Как запустить

```bash
# 1. прокси (upstream указывайте БЕЗ /v4 — путь приходит вместе с ним)
python3 collector/apiscope.py --port 8099 --log scope.jsonl

# 2. публичный адрес: сервер в облаке до вашего localhost не достучится
cloudflared tunnel --url http://localhost:8099
#   → https://что-то.trycloudflare.com

# 3. значения из ВАШЕГО тестового Pyrus
cat > fixtures.json <<'EOF'
{"task_id": 372965117, "form_id": 1504224, "catalog_id": 100500,
 "list_id": 42, "member_id": 777, "file_id": 449339042}
EOF

# 4. прогнать инструменты по одному
python3 collector/probe_tools.py \
    --url https://pyrus-mcp-production.up.railway.app/mcp \
    --bearer $MCP_BEARER \
    --api-url https://что-то.trycloudflare.com/v4 \
    --log scope.jsonl --inventory inventory.json --fixtures fixtures.json
```

Получаете `MAPPING.md`:

| Инструмент | Запросов | Эндпоинты |
|---|--:|---|
| `get_task` | 1 | `GET /v4/tasks/372965117` |
| `get_tasks` | 3 | `GET /v4/tasks/101`, `/102`, `/103` |
| `get_upload_target` | 0 | _ни одного_ |

Плюс по каждому инструменту — какие query-параметры и ключи тела сервер реально
отправляет, коды ответов, размеры, тайминги. И `resp_shape` в `scope.jsonl` —
форма ответа Pyrus с типами полей, то есть готовая схема для вашей реализации.

Строка `get_tasks → 3 запроса` — иллюстрация того, зачем это нужно: их
документация утверждает, что пачка «экономит обращения, но не квоту Pyrus».
Здесь это видно измеримо, а не на слово.

Строка `get_upload_target → 0 запросов` — второй интересный случай: инструмент
конструирует ответ сам, не ходя в API. Такие в `COVERAGE.md` выглядят как
«не ложится на метод», и теперь понятно почему.

## Безопасность лога

`Authorization`, `X-Pyrus-Security-Key`, `X-Pyrus-Access-Token`, поля
`security_key` / `access_token` / `password` / `token` в телах — маскируются
(`<21 симв., …-abc>`). Проверено тестом: настоящий токен в `scope.jsonl` не
попадает. Тела запросов обрезаются до 4 КБ, ответы пишутся **схемой**, а не
содержимым, — рабочие данные в лог не утекают.

## Осторожность

`probe_tools` по умолчанию трогает только инструменты с `readOnlyHint: true`.
Список `NEVER` внутри дополнительно блокирует `delete_task`, `delete_list`,
`sync_catalog` и прочее разрушительное — даже если аннотация врёт. Пишущие
включаются флагом `--write`, и делать это стоит **только на тестовом контуре
Pyrus**.

Ещё две вещи, о которых стоит помнить. Сервер может проверять, что `api_url`
ведёт на домен Pyrus, — тогда приём не сработает, узнаете за одну попытку.
И `probe_tools` читает файл лога напрямую, поэтому запускать его надо на той же
машине, где живёт `apiscope`.

## Проверено на связке целиком

Поднимается фейковый Pyrus, перед ним apiscope, перед ним мок MCP, который
реально ходит в `api_url`. Прогон даёт правильную карту: 1 запрос у `get_task`,
3 у `get_tasks`, 0 у `get_upload_target`, коды 200, секреты замаскированы.

```bash
python3 collector/fake_pyrus.py --port 8091 &
python3 collector/apiscope.py --port 8099 --upstream http://127.0.0.1:8091 --log scope.jsonl &
python3 collector/mock_mcp_server.py --port 8765 &
python3 collector/mcp_introspect.py --url http://127.0.0.1:8765/mcp --bearer test
python3 collector/probe_tools.py --url http://127.0.0.1:8765/mcp --bearer test \
    --api-url http://127.0.0.1:8099/v4 --log scope.jsonl
python3 collector/apiscope.py --show scope.jsonl
```

# 2. Банк решений

## Что это

MCP-сервер поверх Postgres. Хранит версионно: решения, универсальные функции,
успешные кейсы, данные по клиентам, конфигурации ботов, регламенты. Люди и
агенты кладут туда находки и ищут их оттуда.

Три идеи, на которых всё держится:

**Версии неизменяемы.** Правок «на месте» нет. Любое сохранение создаёт новую
версию, старая остаётся навсегда. Поэтому «а как было в марте» — обычный
запрос, а не археология. Если содержимое не изменилось, версия не создаётся:
`content_hash` это ловит.

**Зоны вместо общей свалки.** У каждого своя зона, в неё пишут свободно. Есть
командные зоны. Есть одна общая — и в неё **нельзя писать напрямую**, только
через `propose_promotion` и одобрение ревьюера. Это ровно то разделение, которое
вы просили: пополняют все, но общий банк не превращается в помойку.

**Обратная связь — часть контракта.** Применили чужое решение — вызовите
`record_usage`. Доля успеха с байесовским сглаживанием входит в ранжирование
множителем 0.85–1.15: полезное поднимается, но одна случайная отметка не
выбрасывает свежую запись на первое место.

## Инструменты

| Инструмент | | Что делает |
|---|---|---|
| `list_zones` | чтение | какие зоны вам доступны |
| `search` | чтение | гибридный поиск: полнотекстовый + векторный, слияние по RRF |
| `get_entry` | чтение | запись в текущей версии, со связями и оценкой |
| `get_version` | чтение | конкретная версия целиком |
| `list_versions` | чтение | история: кто, когда, с какой пометкой |
| `diff_versions` | чтение | unified diff текста + изменения ключей payload и тегов |
| `put_entry` | **пишет** | сохранить; повтор того же содержимого версию не плодит |
| `archive_entry` | **пишет** | убрать из выдачи; версии остаются |
| `link_entries` | **пишет** | supersedes / depends_on / variant_of / derived_from / see_also |
| `propose_promotion` | **пишет** | предложить версию в общий банк |
| `list_promotions` | чтение | очередь заявок; помечает, можете ли вы её судить |
| `review_promotion` | **пишет** | одобрить, отклонить или отозвать |
| `record_usage` | **пишет** | helped / partial / failed |
| `stats` | чтение | что вообще лежит в банке |

## Поиск

Гибридный: полнотекстовый поиск Postgres по русской конфигурации плюс векторный
по pgvector, результаты сливаются алгоритмом Reciprocal Rank Fusion (k=60).

Две вещи, которые стоит знать:

**Полнотекстовая часть ищет по ИЛИ, а не по И.** Стандартные
`websearch_to_tsquery` и `plainto_tsquery` склеивают слова через AND, и на
вопросе в свободной форме — «почему реестр теряет закрытые задачи» — это почти
всегда даёт ноль результатов. Мы заменяем `&` на `|` и полагаемся на
`ts_rank_cd`: он сам поднимает документы, где совпало больше слов. Нужна точная
фраза — возьмите её в кавычки, тогда включается `websearch_to_tsquery`.

**Без эмбеддингов сервер работает.** Если `EMBEDDING_URL` не задан, векторная
часть просто не выполняется, а в ответе приходит `"mode": "text"` и пояснение
почему. Это нормальный режим для первого дня: наполняйте банк, эмбеддинги
досчитаете потом.

## Что проверено

`smoke_test.py` проходит весь путь и делает 27 проверок — все зелёные:

- зоны заводятся автоматически при первом обращении;
- запись, повтор без изменений (версия не растёт), правка (версия 2), история;
- дифф: текст, новые ключи payload, новые теги;
- **права**: в общую зону напрямую нельзя, в чужую личную нельзя;
- **промоушен**: заявка → повторная отклоняется → не-ревьюер получает отказ →
  ревьюер одобряет → запись появляется в общей зоне со ссылкой на оригинал;
- **поиск** находит продвинутое решение, фильтры по типу и тегам работают;
- **изоляция**: чужая личная запись не всплывает ни в поиске, ни по прямому id;
- обратная связь пишется и считается, связи создаются, статистика собирается.

```bash
BANK_URL=http://127.0.0.1:8080/mcp BANK_TOKEN=... python3 bank/smoke_test.py
```

## Чего в тестах не было — проверьте у себя

Честный список, чтобы вы не приняли зелёные галочки за большее, чем они есть.

**Векторный поиск не выполнялся.** В среде, где это писалось, pgvector не
собирался, а драйвер Postgres не устанавливался — тесты шли через прослойку над
`psql`, с типом `vector`, подменённым на `text`. Проверены: схема, права, RRF,
промоушен, изоляция зон, полнотекстовая часть. Не проверены: `<=>`, HNSW-индекс,
и сама ветка слияния двух списков в RRF (текстовая ветка работает).
Первым делом после `docker compose up` прогоняйте `smoke_test.py` на настоящем
pgvector с заданным `EMBEDDING_URL`.

**Транзакции.** Прослойка работала в автокоммите, так что `commit`/`rollback`
тестами не покрыты. Один явный `rollback` есть в `propose_promotion` при
конфликте уникальности.

**Нагрузка.** Ни поиск, ни HNSW не мерялись на объёме. HNSW-индекс в схеме
создаётся сразу; на большой первичной заливке его лучше создавать после неё.

## Что стоит добавить, когда банк поедет

- **Фоновый пересчёт эмбеддингов.** Сейчас вектор считается синхронно при
  записи, и если провайдер лежит — запись всё равно сохраняется, но без вектора.
  `stats` показывает, сколько версий без эмбеддинга. Отдельный воркер, который
  их дозаполняет, — первое, что понадобится.
- **Дедупликация при промоушене.** Сейчас проверяется только совпадение slug.
  Полезно предупреждать «в общей зоне уже есть похожее» по векторной близости.
- **Ретеншен для клиентских данных.** `kind='client'` копит версии вечно. Если
  там персональные данные — нужна политика удаления, а `entry_version` устроен
  так, что удаление придётся делать явным инструментом.
- **Разделение токенов.** Сейчас `BANK_TOKEN` один на всех, а личность — в
  заголовке, то есть любой обладатель токена может назваться кем угодно. Внутри
  команды это приемлемо; наружу — нужен токен на человека или OIDC.

# 3. Лаборатория Pyrus API

## Зачем отдельно от прокси

Прокси показывает, что делает **чужой сервер**. Лаборатория выясняет, как себя
ведёт **сам Pyrus** — и это то, что нужно для выгрузки периодами. Идти напрямую
быстрее и чище: вы контролируете каждый параметр, не нужен туннель, никакой
зависимости от автора.

## Главный приём: детектор эффекта

Pyrus на неизвестный параметр отвечает `200` и **полной выборкой**. Значит по
коду ответа судить нельзя: опечатка в имени фильтра выглядит как успешный
запрос, и вы получите неотфильтрованные данные, считая их отфильтрованными.

Лаборатория сравнивает каждый замер с базовым и выносит один из трёх вердиктов:

- ✅ **подействовал** — результат изменился;
- ⚪ **принят, но результат не изменился** — вот он, опасный случай;
- ❌ **отклонён** — честная ошибка.

В набор проб включён заведомо несуществующий параметр как контроль. Если он
получает ⚪ — молчаливое игнорирование на вашем контуре подтверждено.

## Что измеряет

| Раздел | Что выясняет |
|---|---|
| Флаги реестра | сколько задач скрыто без `include_archived`; какие параметры действуют |
| Размер ответа | во сколько раз сжимают `field_ids` и `item_count`, в байтах и примерных токенах |
| Окна по датам | 365 / 90 / 30 / 7 дней: сколько окон на период, максимальный ответ, медиана времени |
| **Граница окна** | включителен ли `created_after` — от этого зависят дубли или пропуски на стыках |
| Журнал событий | какие из пяти CSV-выгрузок доступны и принимают ли диапазон дат |
| История задачи | есть ли у комментариев время и следы переходов — годится ли для process mining |

Про границу стоит сказать отдельно. Их руководство советует «запомнить самую
свежую `create_date` и использовать её как начало следующего окна». Если
`created_after` включительный, такая склейка **дублирует по записи на каждом
стыке**. Лаборатория проверяет это опытом: берёт пограничную задачу и смотрит,
придёт ли она во второй выборке.

## Запуск

```bash
export PYRUS_LOGIN=you@example.com
export PYRUS_SECURITY_KEY=...
python3 lab/pyruslab.py --form-id 1504224 --task-id 372965117
```

Только чтение, ни одного изменяющего вызова. Бюджет запросов по умолчанию 200
при лимите Pyrus 5000 за 10 минут; полный прогон укладывается примерно в 40.

На выходе `LAB.md` и `LAB.json`. Фрагмент реального прогона на заглушке:

```
Без include_archived реестр отдаёт 681 задач вместо 3046.
Скрыто 2365 задач — 77.6% выборки, молча.

| Запрос            |   Байт  | ≈ токенов | Сжатие |
| всё как есть      |  3.2 МБ |   831 502 |     0% |
| + item_count=100  | 106.6 КБ|    27 298 |    97% |
| + field_ids       | 917.3 КБ|   234 818 |    72% |
| + то и другое     |  30.1 КБ|     7 710 |    99% |

Рекомендация: окно 90 дней — 9 запросов на период, ответ меньше 1 МБ.

Пограничная задача 301546 при повторном запросе пришла снова.
Правило: created_after включает границу — дедуплицируйте по id
либо сдвигайте начало на +1 секунду.
```

## Что проверено

Заглушка `fake_pyrus_rich.py` содержит 3046 задач, из них 2365 закрытых,
разбросанных по шагам 1..20 — закрытые намеренно **не** только на последнем
шаге, чтобы ловить наивную догадку. Лаборатория на ней даёт ровно заложенные
цифры.

Важнее другое: заглушка умеет менять поведение, и вердикты меняются вслед за
ним, а не остаются одинаковыми.

| | обычная заглушка | `--strict-params --exclusive-boundary` |
|---|---|---|
| несуществующий параметр | ⚪ принят, результат не изменился | ❌ отклонён (400) |
| граница включительна | да | нет |
| правило склейки окон | дедуплицировать | брать `create_date` как есть |

То есть детектор определяет, а не печатает заранее известный ответ.

```bash
python3 lab/fake_pyrus_rich.py --port 8092 &
PYRUS_LOGIN=y PYRUS_SECURITY_KEY=k python3 lab/pyruslab.py \
    --api-url http://127.0.0.1:8092/v4 --form-id 1504224 --task-id 1
```

# Как это связано с Pyrus-проектом

Сборщик даёт спецификацию railway-сервера. Дальше два пути расходятся:

**Договорились с автором о доступе** — подключаете railway как есть, а банк
решений используете для того, ради чего он и нужен: копить находки по формам,
маршрутам, справочникам, конфигурациям клиентов и ботов.

**Не договорились** — `COVERAGE.md` становится техзаданием на доработку форка
gdigora, `TOOLS.md` — образцом того, как формулировать инструменты, а
`MAPPING.md` показывает, какие вызовы Pyrus за каждым из них стоят. Втроём это
почти спецификация: схемы параметров переносятся дословно, эндпоинты известны
из наблюдения, формы ответов лежат в `scope.jsonl`.

В обоих случаях банк решений живёт своей жизнью и от Pyrus не зависит.
